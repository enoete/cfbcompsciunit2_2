Why this is the most useful thing you'll learn all term

Open your phone. Nearly everything on the screen is the result of a search or a sort that finished before you noticed it happened.

  • Typing a name into Contacts — that's a search.
  • WhatsApp putting the newest chat at the top — that's a sort.
  • Checking a price online — a search across millions of products.
  • A leaderboard, a playlist by date, a class ranked by grade — sorts, all of them.

And here's the hook for the whole lesson: sorting and searching are best friends. Data that has been sorted can be searched in a way that is almost unfairly fast. That single relationship is the reason sorting exists at all.

The register vs the phone book

A teacher's class register is in whatever order students signed up. To find one name you read down the list until you hit it. No shortcuts.

A phone book is alphabetical. Nobody starts at page 1 — you flip to roughly the middle, see whether you've gone too far, and jump again. Two or three jumps and you're there, in a book of thousands of names.

Same task. Wildly different speed. The only difference is that one of them was sorted first.

Linear search — check everything

Looking for your keys

You've lost your keys somewhere in the house. You check the kitchen. Not there. The bedroom. Not there. The sitting room. Not there. The bathroom — got them.

You didn't do anything clever. You checked every room until you found them. That's linear search, and its honest description is: look at everything until you find it or run out of things.

It sounds too simple to deserve a name. But it's the only search that works on unsorted data, which is most data most of the time — so you'll write it more often than anything else in this lesson. Let's build it.

Building it, one cell at a time

Cell 1 — the data.

Eight test scores for a small class. Two things to notice: array indexes start at 0, not 1, so eight scores occupy positions 0 to 7. And C does not remember how big an array is, so we keep the size in n ourselves.

In [1]:
int scores[8] = {72, 45, 91, 63, 88, 55, 79, 34}; int n = 8; printf("Loaded %d scores.\n", n); printf("First is %d, last is %d\n", scores[0], scores[n-1]);
Out[1]:
Loaded 8 scores. First is 72, last is 34
scores[n-1] is the last one — a habit worth forming.
Cell 2 — walk the whole array.

A for loop with i going from 0 up to (but not including) n. Say it out loud as "start at zero, keep going while i is less than n, add one each time". Almost every array program you write starts with this exact line.

Out[2]:

Eight lines out, because the loop ran eight times.
Cell 3 — ask a question inside the loop.

Now add an if. We're hunting for 88. Note == with two equals signs — that's "is equal to". One equals sign would assign 88 and quietly break everything.

In [3]:
int target = 88; for (int i = 0; i < n; i++) { printf("Checking index %d (%d)... ", i, scores[i]); if (scores[i] == target) { printf("MATCH!\n"); } else { printf("no\n"); } }
Out[3]:

Spot the waste — it found it at index 4 and kept going anyway.
Cell 4 — stop when you find it.

Once you've found your keys you stop searching the house. break jumps straight out of the loop. Look at the output: three fewer checks, same answer. That saving is the entire game in this lesson.

In [4]:
int found = -1; // -1 means "not found yet" for (int i = 0; i < n; i++) { printf("Checking index %d... ", i); if (scores[i] == target) { found = i; printf("MATCH!\n"); break; // leave the loop immediately } printf("no\n"); } printf("Result: index %d\n", found);
Out[4]:
Checking index 0... no Checking index 1... no Checking index 2... no Checking index 3... no Checking index 4... MATCH! Result: index 4
5 checks instead of 8.
Why −1 and not 0?

If the function returned 0 for "not found", you could never tell that apart from "found it at index 0" — a real position. −1 can never be a valid array index, so it's a safe way to say nothing here. You met the same trick last lesson when an empty stack had top = -1. Programmers call this a sentinel value.

Cell 5 — wrap it in a function.

Now it's reusable. Give it any array, any size, any target. Notice there's no break — return leaves the whole function at once, which is even more direct. If the loop finishes without returning, the last line runs and reports failure.

In [5]:
int linearSearch(int arr[], int n, int target) { for (int i = 0; i < n; i++) { if (arr[i] == target) { return i; // found — hand back the position } } return -1; // ran out of array — not here } // try it out printf("88 -> %d\n", linearSearch(scores, n, 88)); printf("34 -> %d\n", linearSearch(scores, n, 34)); printf("60 -> %d\n", linearSearch(scores, n, 60));
Out[5]:
88 -> 4 34 -> 7 60 -> -1
Three calls, three different stories.
Cell 6 — always handle the failure.

Returning −1 is useless if nobody checks for it. This is the pattern your marker wants to see: call it once, store the answer, then branch on it.

In [6]:
int pos = linearSearch(scores, n, 60); if (pos == -1) { printf("60 is not in the list.\n"); } else { printf("60 found at index %d.\n", pos); }
Out[6]:
60 is not in the list.
Never print "found at -1". It happens more than you'd think.

The three cases, and the words for them

Best case: it's the first element. 1 comparison.
Worst case: it's last, or missing entirely. n comparisons.
Average case: roughly n/2.

We write the worst case as O(n) and say "oh of n". It means: double the data, double the work. A list of 1,000 needs up to 1,000 checks. A list of a million needs up to a million.

Binary search — throw away half, every time

The guess-my-number game

I'm thinking of a number between 1 and 100. You guess, I say "higher" or "lower".

Guessing 1, then 2, then 3 is linear search — up to 100 guesses. But guess 50 first. I say "higher", and you've just deleted half the numbers in one move. Guess 75. "Lower" — half again. 62... 56... 53...

You will always win in 7 guesses or fewer. For 1 to 1,000,000 you'd need only 20. That's binary search, and it is one of the genuinely beautiful ideas in computing.

The price of admission

The data must already be sorted. No exceptions, no "mostly sorted".

Think about why: the whole trick is that when the middle value is too small, you can throw away everything to its left without looking at it. That's only safe if you know everything to the left is smaller. On unsorted data you'd be discarding the answer half the time — and the algorithm wouldn't crash, it would just confidently tell you the value isn't there.

Three pointers do all the work

Binary search tracks the region still worth looking at with two variables, and inspects its midpoint with a third:

  • first — the left edge of what's still in play
  • last — the right edge
  • middle — dead centre, worked out as (first + last) / 2

Each comparison moves first or last so the region shrinks by half. When they cross, there's nothing left and the value isn't there.

Cell 7 — sorted data, and the midpoint.

Ten sorted values. Watch the integer division: (0 + 9) / 2 is 4.5 in maths, but C throws away the fraction and gives 4. That's fine — we just need a middle, not a perfect one.

In [7]:
int sorted[10] = {12, 19, 23, 31, 45, 52, 64, 78, 85, 97}; int n = 10; int first = 0; int last = n - 1; int middle = (first + last) / 2; printf("first=%d last=%d middle=%d\n", first, last, middle); printf("The middle value is %d\n", sorted[middle]);
Out[7]:
first=0 last=9 middle=4 The middle value is 45
(0+9)/2 = 4 in C, not 4.5. Integer division always rounds down.
Cell 8 — one comparison, by hand.

We want 78. The middle holds 45. Since 78 is bigger and the list is sorted, everything from index 0 to 4 is too small. Gone. Five values eliminated by looking at one.

In [8]:
int target = 78; if (sorted[middle] < target) { printf("%d < %d, so look RIGHT\n", sorted[middle], target); first = middle + 1; // +1: middle itself is ruled out too } else if (sorted[middle] > target) { printf("%d > %d, so look LEFT\n", sorted[middle], target); last = middle - 1; } else { printf("Found it!\n"); } printf("Still in play: index %d to %d (%d values)\n", first, last, last - first + 1);
Out[8]:
45 < 78, so look RIGHT Still in play: index 5 to 9 (5 values)
One comparison. Ten candidates became five.
Why middle + 1 and not just middle?

We already checked the middle — it wasn't the target. Leaving it in the region means the search can get stuck examining the same element forever: an infinite loop that freezes your program with no error message.

This is the single most common binary search bug. The rule is: every comparison must make the region strictly smaller.

Cell 9 — put it in a loop.

Now repeat until found, or until the region collapses. The condition first <= last means "there is still at least one value left to check". When first overtakes last, the region is empty and we stop.

Critical: middle is recalculated inside the loop, at the top. Forget that and you keep testing the same spot forever.

In [9]:
first = 0; last = n - 1; int steps = 0; while (first <= last) { middle = (first + last) / 2; // recalculate EVERY time steps++; printf("Step %d: checking index %d (%d)\n", steps, middle, sorted[middle]); if (sorted[middle] == target) { printf(" Found %d after %d steps!\n", target, steps); break; } else if (sorted[middle] < target) first = middle + 1; else last = middle - 1; }
Out[9]:
Step 1: checking index 4 (45) Step 2: checking index 7 (78) Found 78 after 2 steps!
Two steps. Linear search would have taken eight.
Cell 10 — the finished function.

Same logic, packaged. Compare it line for line with linearSearch from Cell 5: same signature, same −1 for failure. From the outside they're interchangeable. Only the speed differs.

In [10]:
int binarySearch(int arr[], int n, int target) { int first = 0, last = n - 1; while (first <= last) { int middle = (first + last) / 2; if (arr[middle] == target) return middle; else if (arr[middle] < target) first = middle + 1; else last = middle - 1; } return -1; } printf("12 -> %d\n", binarySearch(sorted, 10, 12)); printf("97 -> %d\n", binarySearch(sorted, 10, 97)); printf("50 -> %d\n", binarySearch(sorted, 10, 50));
Out[10]:
12 -> 0 97 -> 9 50 -> -1
50 sits between 45 and 52, so it genuinely isn't there.

How fast is "throw away half"?

Every step halves what's left. So the question "how many steps?" becomes "how many times can I halve this before I reach 1?" That's a logarithm — which is why we call it O(log n).

Numbers make it real:

List sizeLinear search (worst)Binary search (worst)Binary is faster by
1010 checks4 checks2.5×
100100 checks7 checks14×
1,0001,000 checks10 checks100×
1,000,0001,000,000 checks20 checks50,000×
1,000,000,0001 billion checks30 checks33,000,000×

Read that last row again. A billion names, and binary search finds any one of them in thirty questions. Multiply the list by a thousand and binary search needs about ten more steps. That is what O(log n) means in your bones.

Three ways students break binary search — worth reading before you write one

1. Forgetting to recalculate middle inside the loop. If middle is only set once before the loop, you test the same element forever. The program hangs. No error, no crash, just a frozen terminal.

2. Writing first = middle instead of first = middle + 1. When the region shrinks to two elements, it stops shrinking — same infinite loop.

3. Using it on unsorted data. No crash, no warning. It simply returns −1 for values that are definitely in the array. If binary search "can't find" something you can see with your own eyes, check whether the array is actually sorted.

When linear search actually wins

Binary search isn't free. It demands sorted data, and sorting takes real work. So:

  • Searching once, on unsorted data? Linear. Sorting first would cost more than the search saves.
  • Searching over and over? Sort once, then binary search forever. The sort pays for itself after a handful of lookups.
  • Tiny list? Linear. On 10 items nobody can tell the difference, and linear is four lines.

Bubble sort — nudge your neighbour

The school photo line-up

A teacher needs the class lined up shortest to tallest. She doesn't measure everyone and calculate positions. She walks the line and compares just two people at a time: "you two — swap." Then the next pair. Then the next.

One walk down the line, and the tallest person has been pushed all the way to the end — because every time she met them, they were the taller one. Walk again and the second-tallest settles. Keep going and the line sorts itself, with nobody ever comparing anything except their immediate neighbour.

That's bubble sort. Big values "bubble" to the end like air rising in a glass of soda.

The swap — and why it needs a third variable

Before any sorting, one small thing has to be right. Swapping two values in C is not one line, and the reason is worth a minute.

Cell 11 — the broken swap.

The obvious approach destroys data. Run it and watch both variables end up the same. The moment a = b runs, the old value of a is gone — overwritten, unrecoverable.

In [11]:
int a = 5, b = 9; printf("before: a=%d b=%d\n", a, b); a = b; // a is now 9 — and the 5 is GONE FOREVER b = a; // b = 9. We just copied 9 onto itself. printf("after: a=%d b=%d\n", a, b);
Out[11]:
before: a=5 b=9 after: a=9 b=9 <-- the 5 is lost
Two variables, one value. Data destroyed.
Cell 12 — the correct swap.

Park one value somewhere safe first. temp is that safe place. Same idea as last lesson, where you needed a temp pointer before moving head — never overwrite something until a copy exists elsewhere.

In [12]:
int a = 5, b = 9, temp; printf("before: a=%d b=%d\n", a, b); temp = a; // 1. copy a somewhere safe (temp=5) a = b; // 2. now a can be overwritten (a=9) b = temp;// 3. put the saved value back (b=5) printf("after: a=%d b=%d\n", a, b);
Out[12]:
before: a=5 b=9 after: a=9 b=5
Three lines, in this order, every time.

Now build the sort

Cell 13 — one pass down the line.

Compare each neighbouring pair, swap if they're out of order. The loop stops at n-1 because j+1 must stay inside the array — go one further and you read memory that isn't yours.

Watch the output: after one pass the biggest value, 91, has reached the end. It isn't sorted yet, but one element is now definitely in its final place.

In [13]:
int arr[6] = {40, 11, 91, 7, 24, 63}; int n = 6, temp; for (int j = 0; j < n - 1; j++) { if (arr[j] > arr[j + 1]) { temp = arr[j]; arr[j] = arr[j + 1]; arr[j + 1] = temp; printf("swapped -> "); } else { printf("kept -> "); } for (int k = 0; k < n; k++) printf("%d ", arr[k]); printf("\n"); }
Out[13]:
swapped -> 11 40 91 7 24 63 kept -> 11 40 91 7 24 63 swapped -> 11 40 7 91 24 63 swapped -> 11 40 7 24 91 63 swapped -> 11 40 7 24 63 91 After one pass, 91 is home.
5 comparisons for 6 elements — always n-1.
Cell 14 — repeat until sorted.

One pass places one value. So wrap the whole thing in a second loop and do it n-1 times. This is the nested loop — the shape that makes bubble sort O(n²), and the shape students most often get tangled in.

The clever bit is n-i-1. After pass i, the last i values are already sorted, so don't waste time re-checking them.

In [14]:
for (int i = 0; i < n - 1; i++) { // n-1 passes for (int j = 0; j < n - i - 1; j++) { // shrinking inner loop if (arr[j] > arr[j + 1]) { temp = arr[j]; arr[j] = arr[j + 1]; arr[j + 1] = temp; } } printf("After pass %d: ", i + 1); for (int k = 0; k < n; k++) printf("%d ", arr[k]); printf("\n"); }
Out[14]:
After pass 1: 11 40 7 24 63 91 After pass 2: 11 7 24 40 63 91 After pass 3: 7 11 24 40 63 91 After pass 4: 7 11 24 40 63 91 After pass 5: 7 11 24 40 63 91
Watch the green section grow from the right, one per pass.

The early-exit optimisation — worth marks

If a whole pass happens with zero swaps, the array is already sorted. Carrying on is pure waste. One flag fixes it:

for (int i = 0; i < n - 1; i++) {
    int swapped = 0;                     // assume it's sorted
    for (int j = 0; j < n - i - 1; j++) {
        if (arr[j] > arr[j+1]) {
            /* ...swap... */
            swapped = 1;                  // proved otherwise
        }
    }
    if (swapped == 0) break;            // nothing moved — we're done
}

This is why bubble sort's best case is O(n): hand it an already-sorted array and it finishes after a single pass. Selection sort can't do that — it grinds through every pass regardless.

Selection sort — pick the smallest, put it in front

Picking teams in PE

You scan every single person available, decide who's the best, and call their name. Then you scan everyone still left, pick the best of those, call them. Then again. And again.

Notice how different that is from bubble sort. You don't shuffle people around while you're looking — you look first, then make exactly one move. That difference is the whole personality of selection sort.

Formally: split the array into a sorted part (left, empty at first) and an unsorted part (right, everything). Find the smallest in the unsorted part, swap it to the front of that part, and move the boundary one step right.

Cell 15 — find the smallest.

Before sorting anything, learn this pattern — it's worth marks on its own. Assume the first element is the smallest, then check every other one and update if you find better. Notice we track the position, not just the value, because we'll need to know where to swap from.

In [15]:
int arr[6] = {40, 11, 91, 7, 24, 63}; int n = 6; int position = 0; // assume index 0 holds the smallest for (int d = 1; d < n; d++) { // start at 1 — 0 is our assumption if (arr[d] < arr[position]) { position = d; // found a smaller one printf("New smallest: %d at index %d\n", arr[d], d); } } printf("Smallest overall: %d at index %d\n", arr[position], position);
Out[15]:
New smallest: 11 at index 1 New smallest: 7 at index 3 Smallest overall: 7 at index 3
91 and 24 and 63 never triggered an update — they weren't smaller.
Cell 16 — one pass: find, then swap once.

Now put the smallest where it belongs. The if (position != c) guard skips a pointless swap when the smallest is already in place — swapping an element with itself is harmless but wasteful.

In [16]:
int c = 0, swap; // c = front of the unsorted part position = c; for (int d = c + 1; d < n; d++) if (arr[d] < arr[position]) position = d; if (position != c) { swap = arr[c]; arr[c] = arr[position]; arr[position] = swap; } for (int k = 0; k < n; k++) printf("%d ", arr[k]);
Out[16]:
7 11 91 40 24 63 7 and 40 traded places. Exactly one swap this pass.
Bubble sort would have made four swaps to achieve this.
Cell 17 — the whole thing.

Wrap it in an outer loop that walks c from 0 to n-2. Why stop at n-2? Because once every other element is correctly placed, the final one has nowhere else to be. n-1 passes for n elements — a favourite exam question.

In [17]:
void selectionSort(int arr[], int n) { int position, swap; for (int c = 0; c < n - 1; c++) { position = c; for (int d = c + 1; d < n; d++) if (arr[d] < arr[position]) position = d; if (position != c) { swap = arr[c]; arr[c] = arr[position]; arr[position] = swap; } } }
Out[17]:
Start: 40 11 91 7 24 63 Pass 1: 7 11 91 40 24 63 Pass 2: 7 11 91 40 24 63 Pass 3: 7 11 24 40 91 63 Pass 4: 7 11 24 40 91 63 Pass 5: 7 11 24 40 63 91 5 passes, but only 3 swaps — passes 2 and 4 found the smallest already in place.
Green grows from the LEFT here. Bubble sort grew from the right.

6

Which one, when?

Both sorts are O(n²) and both are too slow for serious data. But they fail differently, and exam questions live in that difference.

Bubble sortSelection sort
Core moveCompare neighbours, swap immediatelyScan for the smallest, then swap once
Sorted region grows fromThe right (largest settle at the end)The left (smallest placed at the front)
Passes for n itemsUp to n−1Always n−1
Comparisons~n²/2~n²/2 — always, no escape
SwapsUp to ~n²/2 — potentially a lotAt most n−1
Best caseO(n) with the swapped flagO(n²) — no shortcut exists
Already-sorted inputDetects it, exits after one passGrinds through every pass anyway
Pick it whenData is nearly sorted alreadySwapping is expensive (big records)
The one-line summary

Selection sort makes fewer swaps. Bubble sort can quit early. Everything else about them is roughly the same.

Why would swaps matter more than comparisons? Because comparing two numbers is cheap, but moving a whole student record — name, ID, address, grades — is expensive. If each item is big, selection sort's promise of at most n−1 moves is genuinely valuable.

(b) Bubble sort, pass by pass

EXAM STYLE

Predict each pass before you reveal it

Write down what you think the array looks like after each pass, then reveal. Getting it wrong here is free; getting it wrong in June is not.

Predict pass 1, then reveal.

(c) How many passes does each sort need?

The answer, and the reasoning

Selection sort: always 5. It's n−1 for n elements, no matter what the data looks like. 6 − 1 = 5.

Bubble sort: 5 by the formula, but this particular array is fully sorted after pass 3. Pass 4 runs and makes zero swaps, which is how a bubble sort with the swapped flag detects that it is finished and stops. So: 3 passes to sort it, 4 to know it is sorted, 5 if you blindly apply n−1. Check this against the swaps column in part (b) above.

Read the wording carefully. "Needed to fully sort" and "n−1 passes" are not always the same number, and examiners have been known to accept either with justification.

How to write a top-band answer to (d)

"Binary search cannot validly be applied to Rand in its original state, because binary search requires sorted data. Traced anyway for the value 9, it examines index 2 (value 8), finds 8 < 9 and discards indexes 0–2, then examines index 4 and reports 9 found there.

This result is correct only by coincidence. The step that discarded indexes 0–2 assumed every value there was smaller than 8, which is false — index 0 holds 40 and index 1 holds 11. The same algorithm on the same array returns −1 for 40, 11 and 7, all of which are present. Binary search on unsorted data gives unpredictable results, with no error or warning. The array must be sorted first, giving 7 8 9 11 24 40, in which binary search finds 9 at index 2 in a single comparison."

Saying "it doesn't work" earns a mark. Showing that it can appear to work, and explaining why that is worse, earns the lot.

(e) Linear search for 27

Model answer

"Linear search starts at index 0 and compares each element with 27 in turn: 40 (no), 11 (no), 8 (no), 7 (no), 9 (no), 24 (no). Having reached the end of the array without a match, it returns −1 to indicate that 27 is not present. Six comparisons were made — the worst case, which for linear search is n comparisons."

Two details earn marks: naming the number of comparisons, and saying what gets returned rather than just "it doesn't find it". Note that linear search is perfectly valid here — unlike (d), no sorting is required.

The corrected version

Every fault fixed, plus the early-exit flag. Compare it line by line with the original — being able to spot the difference is the actual skill.

int i, j, temp;

for (i = 0; i < n; i++) {
    scanf("%d", &array[i]);
}                                    // <-- brace closes the input loop

for (i = 0; i < n - 1; i++) {
    int swapped = 0;
    for (j = 0; j < n - i - 1; j++) {
        if (array[j] > array[j + 1]) {   // j, not d
            temp         = array[j];
            array[j]     = array[j + 1];
            array[j + 1] = temp;
            swapped      = 1;
        }
    }
    if (!swapped) break;                // early exit
}

printf("Sorted list in ascending order:\n");
for (i = 0; i < n; i++) {            // i, not undeclared c
    printf("%d\n", array[i]);
}
The habit worth taking away

When code doesn't work, read the first compiler error, not the last. One missing brace or undeclared variable produces a cascade of twenty errors, and nineteen of them are imaginary. Fix the first, recompile, repeat.

And when code compiles but gives wrong answers, print the array inside the loop — exactly as Cells 13 and 14 did. You cannot debug what you cannot see.
